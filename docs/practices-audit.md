# Common-base practices audit

- **Repo:** `app-fraud-interdiction`
- **Catalog id:** G3 (package `app_fraud_interdiction`, env prefix `SCAMINTERDICT`)
- **Catalogue reference:** [`common-base-practices.md`](https://github.com/portable-genai/.github/blob/main/common-base-practices.md) (checks A1..G7)

This file ships PRE-FILLED with the verdicts the template can honestly claim on the day the repo
is rendered, so a new repo never enters the audit matrix owing an unwritten audit. It is not a
claim that the repo was inspected: re-run each check against the tree and correct the row before
citing this as evidence. The rows marked GAP are the day-one work list, in priority order.

Applicability: a rendered repo ships an `agent/` surface (tool functions plus the A2A card
served at `/.well-known/agent-card.json`), a `ui/` micro-frontend and a full `scripts/` demo
surface, so `[ui]` and `[demo]` checks apply on day one. Only `infra/terraform/` remains a
skeleton, so `[infra]` checks stay partial until the stack is filled in. The agent is scaffolded
and tested but not yet registered with Hrz3; see the R4 row in `COMPLIANCE.md`. A repo with no
user-facing surface should run `make drop-ui` and mark the `[ui]` rows N/A, rather than leaving
a UI half-wired.
**Load-bearing** checks (a FAIL breaks a shared catalog guarantee) are A1-A6, C1-C5, D1-D3 and E1.

| **C1** Identity resolved server-side; client actor/ACL discarded `[all]` **(load-bearing)** | PASS | `InterdictRequest` has no `actor` field; the audit actor and the review maker are both the verified `Principal`. The managed adapter EARNS the word verified: `id_token.verify_token` is called with the configured `SCAMINTERDICT_IAP_AUDIENCE` (three-state; unset or emptied refuses rather than verifying without an audience, which google-auth documents as not verifying it at all) and with IAP's own key set rather than google-auth's OAuth2 default, the issuer is checked here because `verify_token` does not check it, and both the call and the lazy import are wrapped so no caller-supplied header can answer 500. `tests/unit/test_iap_identity.py` runs in this gate; `tests/unit/test_iap_crypto_matrix.py` runs the real verifier over a locally minted key in the `iap-verifier` job, which fails if it skips. **The claim half is the commons decision too (2026-08-26).** `resolve()` no longer constructs a `Principal` at all: everything after the signature check is one `hex_service_kit.federation.principal_from_iap_claims(claims, _FEDERATION_POLICY, source="gcp-iap", include_subject_principal=False)` call, and the cryptography stays in the adapter because the kit's core is pure stdlib with zero runtime dependencies and verifies nothing. `_FEDERATION_POLICY` is a reviewed literal carrying `tenant_from_hosted_domain=True`: this deployment configures no domain map and IAP already restricts the audience to one organisation, so the `hd` claim IS the tenant id here, and that is stated as an OPT-IN rather than left to a fallback. `include_subject_principal` is stated for the same reason: this adapter family leaves the tuple to the group map alone while the `adapters/gcp/iap_identity.py` family grants `user:<subject>` and the difference is an authorization decision, not a formatting one. `tests/unit/test_iap_claim_half.py` guards it, and it was RED first, offline, in three stages. (1) Against the adapter exactly as it shipped the module would not even import: `ImportError: cannot import name '_FEDERATION_POLICY'`, which is the state in which a load-bearing tenant can be emptied by a default nobody wrote down. (2) With only the policy object added and the hand-rolled tail left standing it scored 4 failed / 6 passed, and those four ARE the finding: the `acr` row and the mixed-case `hd` row of the comparison disagreed, and both `test_a_claim_set_from_another_issuer_cannot_become_a_principal` and `test_a_verified_assertion_that_names_nobody_is_refused` reported `DID NOT RAISE`, because with the claim-set precheck removed the hand-rolled tail read `claims["email"]` and built a verified identity out of a token issued by somebody else. (3) After adoption, 10 passed. Three deliberate defects on the fixed tree keep the guard honest: flipping `include_subject_principal` scores 6 failed / 4 passed, clearing `tenant_from_hosted_domain` fails the passthrough guard, and passing a fresh `FederationPolicy()` at the call site instead of the reviewed one scores 4 failed / 6 passed, on the resolved tenant rather than on an attribute. **Two behaviour changes are recorded rather than normalised away.** `assurance` now prefers an `acr` claim where the shipped tail hardcoded `"iap"`; nothing in this repository reads `Principal.assurance` for an authorization decision, so the change is audit-visible only, and IAP assertions do not carry `acr` in practice. The tenant is now lower-cased where the shipped tail passed `hd` through with only `.strip()`; `principal.tenant` is a partition key, so a mixed-case hosted domain would change the partition, and Google normalises `hd` to lower case in practice. Both were found by EXECUTING the commons against this adapter over the same claim sets, not by reading it. |
